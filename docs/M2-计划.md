## 1. M1 收尾结论（已实测，本轮关闭）

设计文档给 M1 定了一个门禁：**"M1 必须先在真机复跑 M0 的能力基线"**，因为 M0 的结论
来自桌面 Node 22，而不是 arm64 libnode。这条本轮已关闭，且**可复现**：

```powershell
.\tools\device\run-baseline.ps1     # 推入基线脚本，用 App 自己的 libnode.so 跑
```

真机（arm64 / Android 16）结果，**15 项全绿**：

```
runtime: v26.4.0  android/arm64  napi 10

ok  node:sqlite import              DatabaseSync,Session,StatementSync,backup,constants
ok  node:sqlite open+query          round-trip ok: {"name":"dsh"}
ok  zlib zstd round-trip            38B from 1280B, magic=true, exports=[4 个 zstd API 齐全]
ok  worker_threads round-trip       worker replied (且 --import preload 下同样可用)
ok  child_process spawn + 管道      captured "dsh-child-ok"
ok  child_process spawnSync         status=0
ok  webcrypto / fetch / AbortSignal.timeout
ok  resolve engine entry / koffi
ok  landlock probe verdict          unusable      ← Android 上的正确答案
```

三点值得记：

1. **`node:sqlite` 真的能开库查询**，不只是能 import（正常配置下它是惰性的，
   只有全文搜索会触发）。这条以前没验证过。
2. **worker 在 `--import` preload 下照常工作** —— 我加的进程内 load hook 没有破坏
   worker 启动，`execArgv` 正常传递，3 个并发 worker 都回了话。子代理/工作流因此可用。
3. **`landlock probe = unusable` 是正确的**：证明我们替换 `node-addon-system` 时保留的
   landlock 半边仍按预期降级。

M0 移交的遗留项也一并了结：

| 遗留项 | 结论 |
|---|---|
| **flock** | 已修：Koffi 调 bionic `flock`（真锁，非 stub）。设计文档给的两条路里选了"补 android-arm64 目标"的等价物 |
| **node-pty** | shim 前提成立（管道 stdio 实测可用），但默认 profile 不挂终端行，所以碰不到 |
| **sharp** | 已替换为 `@dsh-mobile/attachment-android`；**原生转码仍待做** → 归入 M3 |

## 2. 现在到底差什么（实测，非推测）

在真机上量到的布局事实：

```
viewport   : 443 x 984 @ dpr 2.4375
sidebar    : 0,0  56 x 985     ← 固定 56px 栏，占屏宽 12.6%，永不收起
hero       : 56,429  377 x 28
composer   : 56,373  377 x 238
mediaQuery : narrow=true   coarse=true   hover=false   ← 窄屏分支确实在生效
safe-area  : CSS env() 可用
touchPoints: 5
```

按"是否阻塞使用"排序，而不是按工作量：

| # | 问题 | 严重度 | 证据 |
|---|---|---|---|
| **1** | **键盘弹出后输入框被盖住** | **不能用** | 截图 `.m1/release-verify.png`：软键盘遮住 composer 下半部，边打字边看不见自己在打什么 |
| 2 | 56px 固定侧栏常驻，窄屏被吃掉 12.6% 宽度 | 不好用 | 上面的 `sidebar` 矩形；应改为可开合抽屉 |
| 3 | 尾部/工具栏被键盘顶起或裁切 | 不好用 | 需与 1 一起量 |
| 4 | 安全区（刘海/手势条）未显式处理 | 不好用 | `env()` 可用但未见使用 |
| 5 | 浮层/弹窗在小屏上的取位 | 不好用 | 目录浏览对话框实测可用，其余未量 |
| 6 | 触控目标偏小、缺按压态 | 不好用 | 桌面密度假设 |

**结论：只有第 1 项是"不能用"，应当作为 M2 的第一交付。**

## 3. 关键技术约束：客户端插件的构建方式

这一条决定 M2 怎么做，必须先说清楚。

M2 的产出按设计文档是客户端插件 `@dsh-mobile/ui`。而 `dsh-client-modules` 的 README
写得很硬：

> **"the host serves built client bundles, so `pnpm run build` must have produced each
> `lib/client.js` before launch; a missing bundle fails activation loudly."**

即上游客户端插件是 **tsdown 打包产物**。但我们的引擎树是 `--omit=dev` 安装的，实测：

```
tsdown / esbuild / rollup / vite / typescript / react / react-dom   →  全部 ABSENT
```

**这本来像是"必须先搭一套 TS 工具链"，但实测产物的格式避免了这件事。**
一个已发布的客户端 bundle 长这样：

```js
window.__ModuleLoader__.load({
  id: "@deepseek-ai/dsh-client-ui-directory-picker-browse",
  factory: (require) => {
    var module = { exports: {} }; var exports = module.exports;
    let react = require("react");                       // 宿主冻结表提供
    let primitives = require("@deepseek-ai/dsh-client-ui-primitives");
    ...
  }
});
```

**factory-CJS，由宿主解析外部依赖。** 所以可以**像 `node-pty` / `node-addon-system` 那样
手写纯 JS**，落在 `android/plugins/`，由现有 stage 脚本装进树里 —— **零构建步骤**。
这与项目既有做法一致。

其余实测事实：

| 事实 | 值 | 含义 |
|---|---|---|
| 客户端行数量 | **53** | 布局/会话/渲染各行都是独立 bundle |
| 全图声明的 external | 只有 **1 个**（`@deepseek-ai/dsh-api-gateway/client`） | `react` 等由冻结基线表提供；其余都内联进各自 bundle |
| 样式 | 107 个注入 `<style>`，无 id | 每个客户端插件注入自己的 CSS |
| CSS 变量 | **725 个**，有语义命名（`--dsh-*` / `--dsw-*` / `--dsl-*`） | 主题层是稳定的 |
| 类名 | **哈希**：`pI_x6G_sidebarCol`、`hHd-Xa_root` | 选择器脆弱，**不要靠 CSS 猜类名改布局** |

> **判据**：主题可以用 CSS 变量改（稳），**布局必须走组件层**（类名哈希，CSS 覆盖不可维护）。

## 4. 分步计划

### M2.1 键盘安全与安全区（先做，唯一阻塞项）

目标：**软键盘弹出时输入框可见、可输入**。

- composer 与尾部工具条对 `visualViewport` 做响应（键位高度 = `innerHeight - visualViewport.height`）；
- `env(safe-area-inset-*)` 用于底部手势条与顶部状态栏；
- 键盘弹起时滚动到光标位置。

**验收（可自动化，不靠肉眼）**：CDP 让输入框聚焦 → 软键盘弹起 → 断言

```
composer.getBoundingClientRect().bottom  <=  visualViewport.height + 1
```

并附真机截图。这是 M2 唯一一条"能用/不能用"的判据，先拿到它。

### M2.2 移动布局（抽屉化）

目标：侧栏在窄屏变可开合抽屉，主内容占满宽度。

- 触控目标 ≥ 44px；补按压/焦点态；
- 浮层（模型选择、权限选择、工作区、指令菜单）在小屏上的取位与滚动。

**验收**：443px 宽下主内容宽度 > 95%；抽屉可开可关；CDP 断言 + 截图。

### M2.3 组件层插件（按需）

仅当 M2.1/M2.2 证明纯 CSS + 少量 DOM 做不到时，才写 `@dsh-mobile/ui` 客户端插件：

- 手写 factory-CJS，`dsh.client.platform = "web"`；
- 用 `inject` 声明依赖（照 `dsh-client-ui-directory-picker-browse` 的写法）；
- 通过 slot 挂载移动端组件，而不是覆盖哈希类名。

**风险**：需要先精确掌握 primitives / slots / renderer 的 API，工作量不小。
**所以 M2.1 与 M2.2 要尽量不依赖它** —— 这也是把它排在最后的原因。

### M2.4 收尾

- 真机回归：`run-baseline.ps1` + 完整对话 + 键盘断言；
- 更新 README / M1 报告的 UI 章节；出新 APK 与发布说明。

## 6. 验证约定（沿用 M1，不新造）

- **一切结论以真机为准**，模拟器只用来快速迭代；两者不一致时以真机为准（M1 的 5 个 bug
  全部只在真机暴露）；
- UI 类问题**用 CDP 查 DOM 与 `__reactProps`，不要猜坐标**（`adb input tap` 需按设备缩放，
  点偏了不报错）；
- 注意**模态框会在 DOM 里保留下层页面**，元素可以"存在、未禁用、handler 正确"却点不到；
- 平台事实**先探针后写代码**（M1 的 flock/link 都是这样定的，避免写出"能跑但不正确"的 stub）；
- 每次改动跑 `run-baseline.ps1`，它是可复现的门禁。
