|---|---|---|---|
| 1 | `Cannot find package '@deepseek-ai/dsh-app-boot'` | 资产解包到 `files/engine/@deepseek-ai/...`，**不在任何 `node_modules/` 里**，而 ESM 解析器只查 `node_modules` | 打包布局改为 `assets/engine/node_modules/` |

### 11.4 「卡在 starting」的最终根因，以及工作区打不开的两个原因

arm64 真机最终**完整跑通**（`status=running`、界面完整、无任何未捕获错误）。
之前"卡在 starting"与"工作区打不开"共三个原因，**没有一个与 arm64 架构有关**：

| # | 表现 | 根因 | 修法 |
|---|---|---|---|
| 1 | 卡在启动页 | 补丁**只接受 `config`/`disabled`**；试图用补丁改 `name` 会被整条丢弃并只发一条警告，于是原版 sharp provider 照旧加载、照旧失败 | `disabled` 上游行 + `insert` 自己的行 |
| 2 | 日志说引擎好了，UI 仍停在启动页 | `EngineService` 在 `:engine` 进程、`MainActivity` 在主进程，**static 不共享** | 服务把状态写进 `files/engine-state.txt`，UI 轮询 |
| 3 | 工作区按钮**渲染出来但点不动** | 禁用 `directory-picker-auto` **同时移除了 host 后端与客户端插件**；客户端插件负责注册 directory-flow slot，slot 无主时按钮照渲染、点击无反应、且不报任何错 | host 与 client **两半都显式 insert** |

第 3 条最值得记住：`-auto` 这类"双面"行 `inject: ["webServer", "loader"]`，
注入 `loader` 就是为了在运行时挂载配对的客户端插件。**禁用它会连带移除客户端能力。**
这是同一个坑的第三次：（1）`attachments` 被禁用 → file-upload 与 session-controller 一起 pending；
（2）`directoryPicker` 被禁用 → workspace-controller pending；（3）`-auto` 被禁用 → 客户端插件消失。

**判据**：写 profile 前先问两件事 —— 这个行提供的服务有没有被别的行 `inject`？
它有没有副作用（挂载别的插件、注册 slot）？有就必须**替换 provider**，不能 `disable`。

## 1. 最重要的发现：libnode 来源必须自己解决

M0 之后我做了一轮可行性排查，结论是**所有"为 Android 预编译好的 libnode"都不够新**：

| 来源 | Node 版本 | 是否可用 |
|---|---|---|
| nodejs-mobile（capawesome 维护 fork） | **18.20.4** | ❌ 引擎跑不起来 |
| puerts/backend-nodejs | **16.16.0** | ❌ 更旧 |
| Termux `nodejs`（aarch64） | **26.4.0** | ✅ 采用 |
| 自建 NDK 交叉编译 | 任意 | 备选（需 POSIX 构建环境，本机是 Windows） |

**为什么 Node ≥ 20 是硬性要求**（实测，非推断）：

```
$ node18 bin.js --profile web
SyntaxError: The requested module 'node:util' does not provide an export named 'parseEnv'
```

`dsh-app-boot/lib/index.js` 第 4 行是**静态 import** `{ parseEnv } from "node:util"`，Node 18 没有
这个导出，引擎在导入阶段就死。Node 20.19.0 与 22.23.1 都有 `parseEnv`，可用；另外
`commander@15` 声明 `engines.node >= 22.12.0`，所以 **Node 26 满足全部约束**。

> 顺带记一个未解的小谜团：Node 20.19.0 在本机跑 `dsh` 时对任何子命令都**零输出、退出码 0**
> （`--version`、`--help`、`--dump-config` 都一样），而 Node 22 正常。二进制本身没坏
> （`node -e "console.log(1)"` 正常）。没有继续深挖，因为我们不需要 Node 20；记下来以免
> 以后有人踩同一个坑。

## 2. 运行时的获取与改造

Termux 的 node 是一个 **47.4 MB 的动态链接 AArch64 PIE 可执行文件**，`PT_INTERP` 为
`/system/bin/linker64`，`DT_RUNPATH` 指向 `/data/data/com.termux/files/usr/lib`。它依赖 10 个
共享库，全部在 Termux 仓库里有预编译包。

`tools/m1/` 下的脚本完成四件事：

1. **fetch-runtime.ps1** — 拉取 nodejs + openssl/libicu/libsqlite/libffi/c-ares/libc++/zlib
   共 8 个 deb，并解包。
2. **stage-runtime.ps1** — 用 `tools/elf-closure.mjs` 递归解析 `DT_NEEDED` 闭包（**结果：10 个
   .so，0 缺失**，只有 libc/libm/libdl 由 Android 提供），然后：
   - 把 `node` 重命名为 **`libnode.so`**。这一步是必需的：Android 打包只会把 jniLibs 里的
     `lib*.so` 解压到 `nativeLibraryDir`，而**只有这个目录是可执行的**（应用私有数据目录在
     Android 10+ 上是 noexec）。
   - 把 `DT_RUNPATH` 从 Termux 路径**原地改写为 `$ORIGIN`**（新串更短，原地覆盖 + NUL 补齐，
     ELF 偏移全部不变），这样加载器会在 `nativeLibraryDir` 里找到同目录的 .so。
   - 额外补齐**带版本号的 soname 别名**（`libcrypto.so.3`、`libz.so.1`、`libicuuc.so.78`…），
     因为加载器按 `DT_NEEDED` 的精确名字查找。

## 3. 引擎依赖树的一个关键发现：koffi 有 android-arm64 预编译

`npm install --omit=dev --omit=optional` 失败，原因是 **koffi**（FFI 库）的安装脚本在找不到
宿主平台预编译产物时要从源码重建，而本机没有 CMake。追下去有两个重要结果：

1. **koffi 存在 `@koromix/koffi-android-arm64` 预编译包**（1.29 MB 的 `koffi.node`）。
2. **6 个 DSH 包依赖 koffi**，其中包括 **`dsh-session-persistence-jsonl`** ——这正是
   M0 报告 §4 里悬而未决的 flock 风险点。

koffi 的加载路径是写死的：

```js
let pkg = `${process.platform}-${process.arch}`;
names = [`${__dirname}/../../../@koromix/koffi-${pkg}`, ...]
```

即手机上会找 `node_modules/@koromix/koffi-android-arm64`。但这个包**无法用 npm 安装**：它的
`os`/`cpu` 字段是 android/arm64，npm 会拿**宿主**平台校验，无论 `--os`/`--cpu` 都报
`EBADPLATFORM`。所以脚本改为直接解包 registry tarball 到该路径，并用 `--ignore-scripts`
彻底跳过 koffi 的 CMake 重建。

> 这**很可能就是 M0 遗留的 flock 问题的答案**（koffi 提供的 POSIX flock 正是
> `dsh-session-persistence-jsonl` 在 Android 上需要的），但**未经真机验证，不能算已解决**。

## 4. 打包时踩到并修掉的三个平台坑

| # | 症状 | 根因 | 处理 |
|---|---|---|---|
| 1 | 构建脚本在 javac 后中断，报 "NativeCommandError" | PowerShell 5.1 把**原生程序写到 stderr 的任何内容**都变成终止性错误，而 javac 的 deprecation 提示走 stderr | 在调用 javac 期间临时把 `ErrorActionPreference` 放宽，以退出码为准 |
| 2 | 应用代码里的 lambda 编译失败：`cannot find symbol: method metafactory` | 为了保住 Android API 纪律，javac 用 `-bootclasspath android.jar`，这会让 `java.lang.invoke` 不可见，lambda 无法脱糖 | **不用 lambda**，全部改匿名内部类（这是保留 API 校验的代价，已写在构建脚本注释里） |
| 3 | 解包出的 deb 仍是 xz 压缩，`tarfile` 报 `invalid header` | GNU ar 用**尾部斜杠**标记长成员名，字段实际是 `data.tar.xz/`，`.endswith('.xz')` 为假 | 先 `rstrip('/')` 再判断 |

## 5. **最危险的一个坑**：aapt2 在 Windows 上会写出反斜杠路径

APK 构建成功后我做了结构校验，发现 **25,277 条目里有 135,178 个反斜杠字符**：

```
assets/engine\@agentclientprotocol\sdk\LICENSE
```

aapt2 在 Windows 上把**宿主路径分隔符**原样写进了 zip 条目名。这在 zip 规范里合法，但
**Android 的 AssetManager 是按 `/` 切分名字去遍历目录的** —— 一个反斜杠分隔的资源树对
`open()`/`list()` **完全不可见**。若不修，装上之后的表现会是"引擎资产一个都找不到"，
而且极难从现象反推原因。

处理：`tools/zip-add-nativelibs.mjs` 在重打包时把所有条目名的 `\` 规范化为 `/`。
修完实测 **反斜杠 0 个**，且关键文件全部就位。

## 6. 另一个坑：aapt2 会丢弃点号开头的资产

`-A` 打包时**隐藏文件（点号开头）被静默丢弃**，实测 APK 里 0 个点号条目。影响：

- 我的版本标记 `.engine-version` 永远到不了 APK → 已改名 `ENGINE-VERSION`。
- npm 留下的 70 个点号文件（`.eslintrc`、`.nycrc`、`.travis.yml`、`.npmignore`…）一并消失，
  但它们是惰性配置，运行时不需要。

## 8. 应用设计要点

- **`:engine` 独立进程 + 前台服务**：引擎崩了 UI 还在，可以显示错误并重启；长任务切后台不断。
- **单例状态交接**：`EngineService.LocalState` 是 UI 与引擎进程之间的一次性"URL 就绪"交接，
  UI 在启动页可见期间轮询它。跨进程 Binder 回调对这点需求来说是过度设计。
- **启动页**：首次启动要解包 189 MB / 25,442 个文件，必须有进度与失败态（含日志尾和
  "复制诊断"），否则用户看到的是长时间黑屏。
- **WebView 收紧**：`allowFileAccess=false`、`allowContentAccess=false`、
  `allowFileAccessFromFileURLs=false`、`allowUniversalAccessFromFileURLs=false`、
  关闭定位。**理由**：agent 会生成 HTML 并在这里渲染，模型写的页面不能读本地文件。
- **导航钉死在 loopback**：只有 `http://127.0.0.1|localhost` 留在 WebView 内，其余交给系统浏览器。
- **明文流量只对回环开放**：`network_security_config` 白名单只有 127.0.0.1/localhost，
  其余保持平台默认（禁明文）。
- **认证沿用官方流程**：加载 `/?token=...` 一次 → 引擎换成 HttpOnly+SameSite=Strict cookie
  并 302 → 后续 RPC 与 WebSocket 自动带 cookie（协议层已在 M0 实测）。

## 9. 已知问题与后续优化

| # | 问题 | 影响 | 建议 |
|---|---|---|---|
| 1 | **APK 145.9 MB 偏大** | 分发与安装体验 | 最大单项是 `libicudata.so` 31.6 MB：可用 ICU 的 `icupkg` 裁掉非必要 locale，通常能降到 2–3 MB。其次是 6 个 soname 别名副本（约 37 MB，可改用 zip 内重复条目之外的方案，或接受） |

#    "engine ready on port N"      -> 端口解析成功

**重点观察项**（都是本机无法验证、只能真机确认的）：

1. `libnode.so` 能否从 `nativeLibraryDir` 以可执行方式启动（**最大不确定性**）。
2. `$ORIGIN` RUNPATH 能否让加载器找到同目录的 .so。
3. `process.platform` 是否为 `'android'`（决定 `profile/android.patch.yml` 的守卫是否生效）。
4. arm64 Node 26 的 `node:sqlite` / `worker_threads` 能力基线（复跑 M0 的断言）。
5. `koffi` 的 android-arm64 绑定能否加载 → 决定 flock / 会话持久化是否可用（§3）。
6. WebView 对该 cookie 会话与 WebSocket 长连接的支持。
7. 首次解包耗时与冷启动时间。
