## 0. 需求复述与术语

### 0.1 需求

构建 DeepSeek Harness 的 Android 手机版应用（APK）：把 DSH 的 agent 引擎与 Web GUI 一起打包进 APK，在手机上本地启动，用户不需要连接电脑、不需要局域网、不需要 Termux。

### 0.2 关于“完全离线”的重要澄清

必须区分两件事，否则会做出错误的架构决策：

| 能力 | 能否离线 | 说明 |
|---|---|---|
| DSH 引擎（agent 循环、工具、会话、GUI） | ✅ 完全离线 | 本方案要达成的目标，引擎与界面全在手机本地进程内 |
| 大模型推理（DeepSeek API） | ❌ 不能离线 | 模型在云端，**必须有公网**（Wi-Fi 或流量）才能对话 |

因此本方案中“离线”的准确含义是：**离线于桌面端 / 于局域网 / 于任何中转服务器**。手机 App 启动后引擎自给自足，但它仍需要访问 `api.deepseek.com`。若真的要求断网可用，只有两条路：接入本地小模型（需额外集成 llama.cpp 类推理运行时，且手机端 1B~3B 模型的能力与 DSH 的 agent 工具链不匹配），或走云端中转——两者都超出本方案范围，本文档第 8 节给出后续扩展位。

### 0.3 术语

- **引擎（engine）**：`@deepseek-ai/dsh` 加载的 Cordis 插件树进程，提供 agent、工具、会话、RPC 与 HTTP/WS 服务。
- **Web GUI**：`@deepseek-ai/dsh-web-frontend` 的构建产物（React SPA），经引擎内嵌 HTTP 服务提供给浏览器。
- **客户端插件（client plugin）**：DSH 的浏览器侧插件包（`dsh.client` 声明 + `lib/client.js` 构建产物），可在不改动核心包的前提下扩展界面。
- **壳（shell）**：Android 原生层，负责解包、启动引擎、承载 WebView、桥接原生能力。

## 1. 结论摘要

> **进展更新（2026-09-28）**：**M0 已执行并通过**，同时推翻了初稿的一处关键假设
> （"禁用 Landlock 沙箱"是错的，会导致引擎完全无法启动）。完整证据见
> [`M0-报告.md`](M0-报告.md)。下列第 2 条已按 M0 结论修正。

1. **方案可行**。DSH 的分层（宿主层 / 客户端插件层 / profile patch 层）天然支持“换一个平台组合”，手机上可以在**不改动任何 `@deepseek-ai/*` 包源码**的前提下完成移植：Android 端只需新增一个 profile 覆盖层、一个移动端客户端插件、一个原生壳。
2. **最大技术风险不在 UI，而在原生依赖**。审计出 9 处平台相关依赖（第 4 节）。**M0 修正后的结论**：Landlock 沙箱**不再是阻塞项**——无需禁用该行，只要把权限策略钉在"全权"档就永远走不到它的探测；真正待处理的是 **`flock`（会话持久化，M0 已定性）**、**`sharp`（图片附件）** 与 **`node-pty`（待真机确认）**。全部有明确解法，**没有"必须重写内核"的死结**。
3. **第二条硬约束是网络**：构建链下载曾在会话初期完全不通（沙箱间歇性故障），后恢复；工具链现已装齐并**验证可产出可安装 APK**（第 9.2 节）。
4. **里程碑状态**：**M0 已完成（PASS）**，M1（最小 APK）可开工，M2 为移动端 UI 适配（工作量最大的单项），M3 之后逐项补齐原生桥接。
5. **UI 适配是本项目真正的成本中心**。现有前端产物 **零响应式断点**（实测：CSS 中仅有 3 处 `prefers-reduced-motion`，没有任何 `max-width` 媒体查询），是纯桌面布局（左侧栏 + 右侧栏 + 多列面板）。手机上不能靠“浏览器缩放”糊过去，必须新增一个移动端客户端插件重排布局。

## 2. 现状侦察：DSH 是什么，以及它今天的样子

本节所有结论均来自对本机安装产物的实际读取，非推测。

### 2.1 组成

`dsh` 是一个 **profile 启动器**：profile = 按顺序叠加的插件组合包（bundle）patch 层 + 用户自己的 patch。

```
dsh 启动器 (lib/bin.js)
  └── profile: web   ← $DSH_HOME/profiles/web/
        ├── bundle 层:  @deepseek-ai/dsh-base         （共享底座：模型、会话、工具、权限）
        ├── bundle 层:  @deepseek-ai/dsh-web-app      （浏览器界面：Web 服务、传输、客户端插件名册）
        ├── profile 层: cordis.patch.yml              （用户自己的覆盖）
        ├── home 层:    $DSH_HOME/cordis.patch.yml
        └── --patch 层: 命令行追加的覆盖文件          ← 本方案的主要注入点
```

配置树由 `--dump-config` / `--dump-default-config` 可导出，**这意味着我们可以精确控制“手机上到底加载哪些插件”**，无需 fork 任何包。

### 2.2 运行链路（实测）

| 环节 | 实现 | 实测证据 |
|---|---|---|
| HTTP 服务 | `dsh-host-webserver`，`host` 仅接受 `127.0.0.1` / `0.0.0.0`，`port` 默认 3080 | `lib/types/index.d.ts`：`host: z.union([z.const("127.0.0.1"), z.const("0.0.0.0")])` |
| 前端静态资源 | `resolveDistIndex()` 从 `@deepseek-ai/dsh-web-frontend/package.json` 解析 `dist/index.html`，由 `frontend-static` 接管 fallback | `dsh-web-app/lib/index.js:107` |
| 前端产物 | `index.html` + `vendor-*.js` (740 KB) + `index-*.js` (556 KB) + 2 个 CSS；**已自带 `manifest.webmanifest`**（`display:fullscreen`） | `dsh-web-frontend/dist/` |
| 浏览器信任栅栏 | Host 必须是 loopback 或 `trustedHosts` 条目；`Origin` 必须等于 Host；`sec-fetch-site: cross-site` 拒绝 | `dsh-client-connection/README.md`，`src/api-request-trust.ts` |
| 浏览器认证 | 进程随机生成 launch token；打印 `http://127.0.0.1:3080/?token=...`；`GET /` 用 token 换取 **HttpOnly + SameSite=Strict 的签名 cookie**（默认 30 天），随后 302 到干净的 `/` | 同上 |
| RPC / 事件流 | `POST /api/remote.mux` 走 WebSocket；事件流 `$events`；`/api` 下还有 fetch 路由；客户端插件 bundle 走 `/plugins/??...&rev=...` combo URL | `dsh-client-connection`、`dsh-client-modules` README |
| 客户端插件装配 | `window.__ModuleLoader__.load({id, factory})` 惰性注册；`dsh.client` 声明 + `./client` 导出；外部依赖需在 `dsh.client.external` 声明，只有 React / Cordis / 静态 UI 库是基线共享模块 | `dsh-client-modules/README.md` |
| 目录选择器 | `dsh-host-directory-picker-auto` 按绑定的 host 自动挂载 `-native` 或 `-browse` | `dsh-web-app/cordis.patch.yml` |
| `--host 0.0.0.0` | **被启动器显式拒绝**（安全考虑：会暴露 RCE 到网络） | `dsh-web-app/lib/startup.js` |

### 2.3 对手机版的三点直接推论

1. **绑定 loopback 是可行的**：手机上的引擎只服务本机 WebView，`127.0.0.1:3080` 完全满足信任栅栏，**不需要任何认证改造**，也不需要 `--trusted-host`。这是“引擎跑在手机里”相对“引擎跑在电脑上”的一个巨大的安全与工程红利。
2. **认领流程是标准的**：壳加载 `http://127.0.0.1:<port>/?token=<token>` 即可走完换 cookie → 302 的官方流程；只要 WebView 允许本地 cookie，后续 `/api` 调用与 WS 全部自动带上 cookie。
3. **前端是可注入的**：`webserver/index-inject` 支持结构化 index 注入（`head`/`body` 行）、`tapIndex` 支持原始 HTML 变换，客户端插件还能自己注入 `<style>`（`dsh-client-ui-theme/lib/client.js` 里就是这么做的）。**这给了我们在不 fork 前端的前提下做移动端 UI 的三条正规通道**（见 5.2）。

## 3. 总体架构

### 3.1 形态选型对比（结论：选 B）

| 方案 | 引擎位置 | 离线* | 工程量 | 关键缺陷 | 结论 |
|---|---|---|---|---|---|
| A 瘦客户端 | 桌面 / Termux | ✗ | 2–3 周 | 需同网或隧道；`--host 0.0.0.0` 被禁，要改绑定与证书；桌面关机即不可用 | 落选（可作为附赠能力支持） |
| **B 一体化 APK** | **手机本地** | **✓** | **2–4 个月** | 原生依赖移植 + UI 重排；APK 体积 80–150 MB | **采用** |
| C 纯客户端重写 | 无 | ✓ | 极大 | 等于重写 agent 循环 + 工具链 + 会话协议，且永久脱节于上游 | 落选 |
| D React Native / Kotlin 重写 UI | 手机本地 | ✓ | 极大 | 需重写上百个 `dsh-client-ui-*` 包（工具树、审批、轨迹、workflow、goal…） | 落选（仅作远期“原生 UI”可选演进） |

\* 此处“离线”指无需外部引擎，不含模型 API 联网（见 0.2）。

**选 B 的核心理由**：DSH 已经把自己的平台差异全部收敛到了 profile patch 层与少数几个 provider 包里。手机上我们只需要**再提供一份 patch 层 + 一个移动端客户端插件**，就能复用 100% 的 agent 引擎、100% 的 RPC 协议、99% 的 UI 组件。选 D 会把“移植一个前端”变成“重写一个 IDE”，性价比不成立。

### 3.3 为什么引擎要跑在独立进程 `:engine`

| 维度 | 同进程（主进程内起 Node 线程） | **独立进程 `:engine`（采用）** |
|---|---|---|
| 引擎崩溃 | 整个 App 挂掉，用户丢失界面状态 | 界面存活，可提示并一键重启引擎 |
| 内存 | 与 UI 共享上限，WebView 与 Node 峰值叠加易被 LMK 杀 | 独立内存记账，可分别观察；UI 不被引擎峰值拖累 |
| 生命周期 | 随 Activity 死亡 | 可由前台服务保活，切后台不中断长任务 |
| 调试 | 混在一起 | 可单独 `adb logcat` / 重启 |
| 成本 | 略简单 | 需 AIDL 或 Binder + 文件握手（成本可控） |

> 实现注意：Android 上**不能**像桌面那样简单地 `exec` 一个独立 node 可执行文件（可写目录普遍 `noexec`，且 `zygote` 限制）。因此必须在 APK 的 `jniLibs/arm64-v8a/libnode.so` 里携带 Node（该目录天然可执行），再在新进程内通过 JNI 启动。**`libnode.so` 方案同时解决“可执行”与“可分进程”两个问题**（详见 4.1）。

### 3.4 安全模型

| 项 | 决策 | 理由 |
|---|---|---|
| 引擎绑定 | 仅 `127.0.0.1`，**不使用** `0.0.0.0` | 上游已明确拒绝 `0.0.0.0`；本方案根本不需要 |
| 认证 | 复用官方 launch token → HttpOnly cookie 流程 | 零改造，且 token 每次启动随机 |
| WebView 明文流量 | 仅对 `127.0.0.1` 放开（network-security-config 白名单） | Android 9+ 默认禁明文；不要全局 `usesCleartextTraffic` |
| WebView 本地文件访问 | `setAllowFileAccess(false)`、`setAllowUniversalAccessFromFileURLs(false)`、`setAllowFileAccessFromFileURLs(false)` | agent 会生成 HTML 内容，必须防“本地文件读取 + 外发”这条链 |
| 权限沙箱 | 手机上固定 `danger-full-access` + `approval: never`，**显式禁用 Landlock 沙箱行** | 见 4.3：Landlock 是 Linux 专属且 Android 不可用；手机是单用户设备，工作区在应用私有目录内，且引擎只能以本 App 的 uid 运行——**本来就不具备越权能力**，这是“系统的沙箱”替代了“DSH 的沙箱”。必须在首次启动做一次显著告知 |
| 引擎监听端口被其它 App 访问 | 端口随机（`--port 0`）+ token 保护 | 同设备其它 App 若拿到 token 才能调用；配合随机端口进一步降低风险 |
| 凭据存储 | `$DSH_HOME/.credentials.yaml`（应用私有目录） | 免 root 不可读；后续可增强为 Android Keystore 加密 |
| 工作区位置 | 应用私有目录 | agent 无法越界写 `/sdcard`；用户通过“导入/导出”显式交换文件 |

> 如果产品上必须允许 agent 直接读写 `/sdcard/Documents`，那需要走 SAF + 定时同步，属于 M3 之后的可选增强，且要重新评估风险（模型可读写用户真实文档）。

## 4. 关键技术问题与解法

### 4.1 Node 运行时怎么进 APK（P0 决策）

**问题**：Android 应用进程无法从可写目录执行任意二进制（`/data/local/tmp` 等普遍 `noexec`），但 `nativeLibraryDir` 中的 `.so` 可执行。同时需要“可分进程启动”“可控 stdout”“能调用 JNI”。

**候选方案**：

| 方案 | Node 版本 | 说明 | 评估 |
|---|---|---|---|
| **libnode.so + JNI 启动**（`nodejs-mobile` 系） | 取决于 fork | 把 Node 编译为共享库，JNI `startNodeWithArguments()` 启动；社区有可用 fork，如 [capawesome-team/nodejs-mobile](https://github.com/capawesome-team/nodejs-mobile)（原 [JaneaSystems/nodejs-mobile](https://github.com/JaneaSystems/nodejs-mobile) 已停更） | **主选**：成熟路径，解决 noexec，可分进程 |
| 自建 libnode（NDK 交叉编译 Node 22） | 22.x | 用 Android NDK 直接把 Node 22 编成 `libnode.so`，可精确对齐桌面版 Node 22.23.1；参考 [build-javet-node-android](https://github.com/goldenduo/build-javet-node-android)、[puerts/backend-nodejs](https://github.com/puerts/backend-nodejs) | **备选/终局**：可控性最好，但要处理 Node 官方的 Android 支持缺口（configure/编译分支、ICU、OpenSSL） |
| Termux 式原生 node 二进制 | 22.x | 直接把 Termux 的 `node` 放进 APK | 不可行：动态链接 bionic 与 Termux 的 prefix 强绑定，且 `nativeLibraryDir` 只能放 `.so`，可执行路径不成立 |
| PRoot / 完整 Linux 用户态 | 任意 | 在手机里跑一个 Linux rootfs | 落选：体积 +200 MB、性能损耗、Play 政策与体验都不可接受 |

**决策**：M0/M1 用 **nodejs-mobile fork 的 libnode.so** 快速打通（优先确认其 Node 主版本是否 ≥ 22 且是否带 `node:sqlite`）；**M2/M3 评估切换到自建 Node 22 libnode**，以保证与上游 `@deepseek-ai/dsh` 的 engine 要求一致。

**必须满足的 Node 能力清单**（逐项在 M0 用 `node -p` 验证）：

| 能力 | 用途 | 不支持时的降级 |
|---|---|---|
| Node ≥ 22.5 + `node:sqlite` | `dsh-session-query-sqlite`（会话全文检索） | web profile 里 `openAt: never`（惰性），仅影响搜索；可换 `dsh-session-query` 内存实现 |
| `node:worker_threads` | `dsh-code-runtime-worker-thread`、`dsh-workflow-worker-thread` | 禁用对应行，牺牲 code runtime / workflow |
| `node:http` upgrade（WebSocket） | `/api/remote.mux` | 无降级，**必须支持**（否则 RPC 不通） |
| `child_process.spawn('/system/bin/sh')` | bash 工具 | 禁用 `tool-bash`（手机版可接受，见 4.3） |
| `Intl` / `TextEncoder` / `fetch` / `WebCrypto` | 通用 | 无降级，必须支持 |
| `process.platform === 'android'` | base 层的 `!!js` 条件行分流 | 若某些 fork 报 `'linux'`，需在 patch 层显式关闭 pwsh/landlock 行（本方案本来就显式关闭） |

### 4.2 profile 设计（本方案的核心交付之一）

> **本节结论已被 M0 实测修正。** 初稿写的是"禁用 Landlock 沙箱行"，实测证明那样做
> **不是降级而是无法启动**（shell 提供者依赖 `sandbox`，`permission-presets` 依赖 `shell`）。
> 正确做法是**保留全部提供者挂载，只把权限策略对钉到全权档**。
> 完整证据见 [`M0-报告.md`](M0-报告.md) §1、§2.2。

在 web 组合之上叠加一层覆盖（正式产物：`profile/android.patch.yml`）：

```yaml
# android.patch.yml（要点摘录，完整带注释版本见仓库内该文件）
# 唯一必需的改动：权限策略"对"必须成对覆盖
- id: sandbox-policy
  config:
    mode: !!js >-
      process.platform === 'android' ? 'danger-full-access'
      : (process.env.DSH_PERMISSION_MODE ?? 'workspace-write')
- id: approval
  config:
    policy: !!js >-
      process.platform === 'android' ? 'never'
      : ((process.env.DSH_PERMISSION_MODE ?? 'workspace-write') === 'danger-full-access' ? 'never' : 'ask')

# 桌面集成在手机上无对应物（M1 起由原生壳接管）
- id: directory-picker
  disabled: !!js process.platform === 'android'
- id: open-in-app
  disabled: !!js process.platform === 'android'

# M1 之后追加移动端 UI 客户端插件（M0 未纳入，避免混淆变量）
# - insert:
#     - id: ui-mobile
#       name: '@dsh-mobile/ui'
```

**三条关键约束（均由 M0 实测得出）**：

1. **绝不禁用 `sandbox` 行。** `dsh-bash-sandbox` / `dsh-pwsh-sandbox` 都 `inject: [subprocess, sandbox, sandboxPolicy]`，
   而 `dsh-permission-presets` 的 `static inject` 含 `shell`。禁用 `sandbox` 会移除唯一的
   `ctx.shell` 提供者，导致 boot 门禁拒绝启动整个引擎。
2. **`sandbox-policy` 与 `approval` 必须一起覆盖。** 只改前者会让 `permission-presets`
   构造失败（它校验"沙箱+审批"默认组合必须命中某个预设）。
3. **为什么保留沙箱却不被 Landlock 挡住**：`dsh-sandbox-local` 的 Linux runner 链
   `["bwrap","landlock"]` 只在 `confine()`（真正请求约束）时才探测，而 `danger-full-access`
   是"不约束"档，因此走不到探测。**即：Android 上不需要删除沙箱，只需要永不使用约束档。**

**注入方式（三选一，按侵入度递增）**：

1. `dsh --profile web --patch /path/android.patch.yml` —— **推荐**。零改动上游，patch 由壳在启动时以绝对路径传入。
2. `$DSH_HOME/cordis.patch.yml` —— 作为 home 层长期生效，适合“用户级出厂设置”。
3. 自定义 profile 目录 —— 把 `web` 的 bundle 列表复制一份改名 `android`，可完全掌控名册，但需跟随上游升级维护。

### 4.3 平台相关依赖审计（实测结果 + M0 修正）

审计范围：本机已安装的全部 `@deepseek-ai/*` 包（约 180 个）的依赖字段与 import 语句。

| 包 | 依赖 | 是否阻塞启动 | 处理方式 |
|---|---|---|---|
| `cordis-plugin-loader` | `node-addon-require-builtin` | **否（优雅降级）** | 实测调用被 `try { … } catch {}` 包裹，失败即回落 `require('node:module')`；无需 Android 版 addon |
| `dsh` | `node-addon-require-builtin` | 否 | 同上，仅传递依赖 |
| `dsh-sandbox-local` | `@deepseek-ai/node-addon-system`（bwrap/Landlock） | **否，但不可禁用** | **M0 修正**：保持挂载；`danger-full-access` 档不会触发 runner 探测。禁用会让引擎完全无法启动（§4.2） |
| `dsh-bash-sandbox` | `@deepseek-ai/node-addon-system` | 否 | 保持挂载（Android 下上游条件 `process.platform !== 'win32'` 使其启用）。它是 `ctx.shell` 提供者之一 |
| `dsh-session-persistence-jsonl` | `@deepseek-ai/node-addon-system`（flock） | **是（首次会话加锁时）** | **M0 定性**：静态 import 但**绑定惰性加载**，故不影响启动；`process.platform === 'android'` 时 `loadBinding()` 必抛 `ERR_FLOCK_UNSUPPORTED_PLATFORM`。需 NDK 补 android-arm64 目标，或复用上游"单进程免锁"接缝。**M1 决策项**，见 [`M0-报告.md`](M0-报告.md) §4 |
| `dsh-subprocess-local` | `node-pty`、`dsh-win32-process` | **待真机确认** | 静态 import node-pty；web 组合已挂载该行。需 android-arm64 node-pty 或替换提供者 |
| `dsh-attachment-local` | `sharp` | **是（若使用图片附件）** | sharp **无 android-arm64 预编译产物**，Termux 下会自动回落 WASM（[sharp#4563](https://github.com/lovell/sharp/issues/4563)）。决策：手机版附件走**原生层缩放/转码**（Kotlin `ImageDecoder` → JPEG）后再交给引擎，彻底绕开 sharp；或引入 sharp 的 WASM 版。**M0 未验证** |
| `dsh-sandbox-windows-acl` | `dsh-win32-process` | 否 | Android 不加载（上游条件行已分流） |
| `dsh-host-directory-picker-native` / `dsh-host-open-in-app` | `dsh-native-command` | 否 | 手机端由原生壳/Bridge 提供等价能力，这两行在 Android 下禁用 |
| `cordis-plugin-hmr` | `esbuild`（devDependency） | 否 | 实测基线组合里 `hmr` 行本就是 `disabled` |
| `dsh-base` / `dsh-session-reference` | `dsh-session-query-sqlite` | 否 | 惰性 `openAt: never`；仅在启用全文搜索时需要 `node:sqlite`（Node 22 实测可用） |

**结论**：真正需要处理的收敛为 **2 项**（flock、sharp），外加 1 项待确认（node-pty）。
Landlock 从"阻塞项"降级为"无需处理"——这是 M0 最有价值的发现，它把移植难度显著下调。
且**仍不需要改上游包源码**——这正是 profile patch 架构的价值。

### 4.4 `dsh` 进程如何启动、如何拿到 URL/token

**问题**：壳需要知道引擎是否就绪、监听端口是多少、本次的 launch token 是什么。

**方案对比**：

| 方案 | 做法 | 评价 |
|---|---|---|
| **stdout 解析**（M1 采用） | 以 `dsh --profile web --patch <abs> --no-open --port 0` 启动，逐行扫描 stdout 的 `dsh web: http://127.0.0.1:<port>/?token=<token>` | 这是**官方稳定输出**（`dsh-web-app` 的 `printUrl`），零上游改动；缺点：依赖日志格式 |
| 健康检查 | 解析到端口后 `GET /` 直到 200；并设启动超时（如 90 s，首次运行要建 profile） | 必须有；Android 冷启动 + Node 初始化在低端机上可能 >30 s |
| 自定义 bridge 插件（M3 增强） | 写一个极小的 Cordis 宿主插件：`inject: ['connection','webServer']`，把 `connection.authenticatedUrl(...)` 与端口通过 JNI 回调直接交给壳 | 更稳、更快、可上报结构化状态；作为长期方案 |

**启动时序**：

```
App 启动
 ├─ 1. 首启解包：把 assets 里的 node_modules 树与 profile 模板解到 files/dsh-home（耗时 5–30 s，只做一次；记录解包版本号，升级时增量）
 ├─ 2. 起 :engine 进程 → JNI 启动 libnode，argv = [libnode, dsh.js, --profile, web, --patch, <android.patch.yml>, --no-open, --port, 0]
 ├─ 3. 环境变量：DSH_HOME=files/dsh-home, cwd=files/workspace, HOME=files, TMPDIR=files/tmp, DSH_PERMISSION_MODE=danger-full-access
 ├─ 4. 扫描 stdout/日志 → 提取 URL+token → 通过 Binder/文件握手回传主进程
 ├─ 5. WebView 加载 http://127.0.0.1:<port>/?token=<token> → 换 cookie → 302 → GUI
 └─ 6. 常驻：前台服务保活；引擎退出 → 界面显示“引擎已停止/重启”卡片（不静默崩溃）
```

> 注意：`--port 0` 让 OS 分配空闲端口，可取，但要确保解析逻辑正确读取实际端口（`webServer.port` 的实际值会打印在 URL 里）。若发现 `--port 0` 与 url 打印有冲突，退化为固定 3080 + 占用检测。

### 4.5 存储与文件交换

| 路径 | 内容 | 备份策略 |
|---|---|---|
| `files/dsh-home/` | profile、`cordis.patch.yml`、`.credentials.yaml`、会话 JSONL、设置 | 参与 Android 自动备份（可选）；提供“导出诊断包” |
| `files/workspace/` | agent 工作区（会话子目录） | 同上 |
| `files/logs/` | 引擎日志（环形，默认保留最近 N MB） | 只导出 |

**文件进出的三个正规通道**（都必须做，否则手机版是“信息孤岛”）：

1. **导入**：`ACTION_OPEN_DOCUMENT` / `ACTION_GET_CONTENT` → 复制进 `workspace/`（触发 `file-upload` 之外的原生路径）。
2. **导出/分享**：FileProvider + `ACTION_SEND`，把 `ui-deliverables` 列出的产物分享到微信/邮件/其它 App。
3. **用其它 App 打开**：`ACTION_VIEW` + FileProvider（对应 `open-in-app` 的手机端实现）。

### 4.6 模型与凭据

- API Key 写入 `$DSH_HOME/.credentials.yaml`（应用私有目录）。
- 首次启动需要引导：**在引擎就绪前无法用 DSH 自己的设置页**，所以壳需要提供第一屏引导（欢迎 → 说明离线含义与权限模型 → 填入 DeepSeek API Key → 启动）。可用 `dsh-settings` 相关的 RPC 或直接写凭据文件（需确认凭据文件格式与 provider 约定，M1 验证项）。
- 若上游支持，也可复用 Web GUI 内的 `ui-settings-models` 页面做 Key 管理；引导页只做“最少必要”的填写。

### 4.7 ESM 与依赖解析

DSH 全部为 ESM（`"type": "module"`），且 `dsh` 的模块解析依赖 **profiles 目录附近的 `node_modules` 树**。手机端要把整个依赖树随 APK 分发并把 cwd/解析根指到解包目录：

- 打包：在构建机上 `npm install --omit=dev --omit=optional`（跳过 sharp 等无关平台包）到 staging 目录 → 作为 APK 的 `assets/` 或压缩包分发 → 首启解包到 `files/dsh-home/`。
- 校验：解包后做一次“入口可达性”自检（`require.resolve('@deepseek-ai/dsh')`），失败则提示重装而不是无限重启。
- 升级：APK 内携带树版本号；升级时若版本变化则重建解包目录（保留 `dsh-home` 里的用户数据与会话）。

## 5. 移动端 UI 适配（工作量最大项）

### 5.1 实测现状

| 检查项 | 结果 | 影响 |
|---|---|---|
| CSS 媒体查询 | **仅 3 处 `prefers-reduced-motion`，0 处宽度断点** | 无任何响应式布局，纯桌面 |
| `viewport` meta | `width=device-width, initial-scale=1`（已有） | 基础可用，但缺 `viewport-fit=cover`，刘海/手势条会遮挡 |
| 安全区适配 | 未发现 `env(safe-area-inset-*)` | 全面屏上工具栏会被顶到手势条下 |
| 触控支持 | `pointerdown` × 20、`touchstart` × 5 | 有基础指针事件，但缺长按/滑动等移动手势 |
| PWA manifest | 已有（`display: fullscreen`） | 说明“全屏/移动化”并非与上游方向冲突 |

### 5.2 适配通道（由浅入深，建议组合使用）

| 通道 | 机制 | 适合做 |
|---|---|---|
| ① index 注入 | `webserver/index-inject` 的 `style` / `html` / `global` 行，或 `tapIndex` | 注入 `viewport-fit=cover`、`<meta name="theme-color">`、移动端基础 CSS 变量、`window.__DSH_MOBILE__` 标志 |
| ② 客户端插件 `@dsh-mobile/ui`（**主力**） | `dsh.client` + `lib/client.js`，可注入 `<style>`、复用 React 与基线 UI 模块、注册 slot 占位 | 响应式布局重排、移动导航、手势、软键盘与输入坞、设置页的移动化 |
| ③ 原生壳 WebView 注入 | `WebViewAssetLoader` / `evaluateJavascript` | 兜底与热修；不作为主路径（难维护） |

**推荐**：①负责“页面级基础适配”，②负责“结构级重排与交互”，③只在应急时使用。这样手机上跑的还是**同一套上游组件**，上游升级时我们的适配层只需跟着改少量 CSS/插槽。

### 5.3 必须解决的移动端问题清单

| # | 问题 | 方案 |
|---|---|---|
| 1 | 三栏（左会话栏 / 中对话 / 右面板）在 360 dp 宽下不可用 | 断点重排：< 768 dp 时左栏与右栏变**抽屉/底部面板**，中间对话独占；保留会话切换与文件预览入口 |
| 2 | 对话消息与工具调用树横向溢出 | 工具树在窄屏改为纵向折叠；代码块横向滚动；表格降级为卡片列表 |
| 3 | 输入坞被软键盘遮挡 | `windowSoftInputMode="adjustResize"` + CSS `dvh`/`env(keyboard-inset-height)`；输入坞 `position: sticky` 到可视区底 |
| 4 | 手势冲突（返回键 vs 抽屉） | 系统返回键优先关抽屉/弹层；`OnBackPressedCallback` 与前端事件桥接 |
| 5 | `@` 引用、`/` 命令、模型选择等浮层在窄屏溢出 | 浮层改全宽底部弹层（bottom sheet） |
| 6 | 长列表性能（会话很长） | 沿用上游虚拟化；移动端降低默认加载窗口、`content-visibility` |
| 7 | 冷启动与首次交互延迟 | 引擎预热 + 启动骨架屏（原生层先画，不等引擎）；首启解包进度可见 |
| 8 | 深色模式与 OLED | 复用 `ui-theme` 的 `--dsw-*` token；原生状态栏跟随 |
| 9 | 无障碍与字号 | 响应系统字号缩放；最小触控目标 44 dp |
| 10 | 横屏 / 折叠屏 | 平板（≥ 768 dp）恢复多栏；折叠屏铰链区域避让 |

### 5.4 可以后置或裁掉的功能（手机场景低价值）

- 终端（`dsh-terminal`，依赖 node-pty）：手机上价值低、成本高，**建议 v1 不做**，在 UI 里隐藏入口。
- `open-in-app`、`directory-picker-native`：改为壳的原生实现。
- Plan/Trajectory/Workflow 等重型面板：保留但默认折叠。

### 9.2.1 已知环境限制：Gradle 守护进程无法启动

实测结论：**Gradle 在本沙箱内不可用**，任何构建任务都死在

```
Caught exception: Couldn't open current thread, error = 5
```

定位过程与结论：

| 验证 | 结果 |
|---|---|
| `gradle --version`（不启动守护进程） | ✅ 通过 |
| `gradle help` / `tasks` / `assembleDebug`（需守护进程） | ❌ 全部失败 |
| Java 新建线程、线程池 | ✅ 正常 |
| Java 启动子进程（`ProcessBuilder`） | ✅ 正常 |

即：**JVM 本身没问题，是 Gradle 守护进程的启动被拦**。最可能的原因是守护进程通过
`native-platform.dll` 调用 `OpenThread` 并请求 `THREAD_SET_INFORMATION` 权限，
而本沙箱的进程令牌不允许。

**应对（已落地）**：`tools/build-apk-cli.ps1` 绕开 Gradle，直接驱动 SDK 命令行工具链
完成 `aapt2 link → javac → d8 → jar uf → zipalign → apksigner`。
对 M1 的 WebView 壳来说这条路径足够（纯 Java 源码、无复杂资源合并）；
它是无守护进程的可靠后备，也可直接用作后续 release 签名驱动。

**何时必须回到 Gradle**：引入 Kotlin 代码、AndroidX 依赖、复杂资源/aapt2 编译期处理或
多模块构建时。届时的选项：① 在沙箱外（普通终端）跑 Gradle；② 本机放开沙箱权限；
③ 走 CI（GitHub Actions）出包。

### 9.2.2 本机外网状态说明

本会话外网是**间歇可用**的：会话开始时 curl / Invoke-WebRequest / Node `fetch` 全部失败
（`schannel SEC_E_NO_CREDENTIALS`），但随后 Node `fetch` 与 Java HTTPS 均恢复正常，
SDK 组件与 Gradle 发行包因此得以成功下载。结论：**网络故障是沙箱侧间歇性的，
不是配置问题**；下载失败时重试通常即可，命令需带重试逻辑（SDK 安装脚本已带 4 次重试）。

### 9.4 M0 验证套件（已实现：`tools/verify-engine.mjs` + `tools/ws-probe.mjs`）

`tools/verify-engine.mjs`（并配套 `tools/ws-probe.mjs`）逐项断言并输出报告：

1. Node 版本、`process.platform`、`node:sqlite` / `worker_threads` / `child_process` / `fetch` / `WebCrypto` / `AbortSignal.timeout` 可用性；
2. `--dump-config` 在 android patch 下的最终插件树；`--simulate-android` 会把 `!!js process.platform === 'android'` 守卫按 Android 重新求值，从而在桌面预览手机端的树；
3. 提供者图（**ADVISORY，非判据**）：从 `static inject` 推断依赖，标记"消费者有需求但提供者被禁用"的行。**已知不可靠**——健康的基线树也会报约 20 个假阳性（服务名经 `super(ctx)` 动态注册，正则抓不到），因此只应比较两棵树之间的**差量**；
4. HTTP 认证链路：`GET /?token=` → 303、cookie 属性（HttpOnly / SameSite=Strict / Max-Age）、无 cookie 401、带 cookie 200 且含 `__DSH_BOOT__`、静态资源公开；
5. 传输层：`/api/remote.mux` 的 WebSocket 升级（由 `tools/ws-probe.mjs` 覆盖）；
6. 结论输出为 JSON（`--json`），供 CI 与文档引用。

**实现约束**：套件**不自行启动引擎**——本沙箱下 Node 的 `child_process` 管道 stdio 会 EPERM（命名管道限制），`shell: true` 走 cmd.exe 亦被拦。因此由调用方用现成的 shell 导出配置树，套件只做分析与判定。判定依据是**经验证据**：`--engine-up` 表示调用方已实际观察到该配置启动成功，静态分析不能替代它。

**未覆盖（需真机）**：真实模型往返（需 API Key）、会话 JSONL 读写、`sharp`、arm64 libnode 的能力基线。见 [`M0-报告.md`](M0-报告.md) §5。
