# 移动端 UI 设计（M2）

> 依据 `frontend-design` skill 的两阶段流程：**先设计计划，再对着 brief 复核，然后才写代码**。
> 本文是第一阶段 + 复核结论。实测数据来自真机 CDP，不是推测。

---

## 0. 这个 brief 到底要设计什么（先纠正一个前提）

skill 要求先把 subject、audience、job 说清楚。这里有个容易走偏的地方，必须先讲明：

**界面已经有一套完整的设计语言了。** 它由 38 个客户端插件组成，53 个 bundle，
注入 107 个 `<style>`，约 440–725 个语义 CSS 变量，字体栈是
`-apple-system, "PingFang SC", …`（系统字体，非自定义），浅色主题。

所以 M2 **不是**"给一个新产品设计视觉识别"。如果我另起一套配色和排版，会和 38 个插件打架，
而且是在解决一个不存在的问题。**M2 要设计的是"手机形态的结构"**：

| | |
|---|---|
| **Subject** | 一个跑在手机上的**编码智能体**。手机是它唯一的外壳，没有桌面端 |
| **Audience** | 开发者本人，**竖屏单手**，常在通勤/床上、注意力被打断 |
| **Primary job** | 读它的输出、**快速丢一句话进去**、切会话。不是长时间精修代码 |

**这个 job 决定了设计的核心：输入必须是第一公民，会话列表是次要的。**
而现状恰好相反 —— 会话栏常驻占位，输入框被挤在中间。

## 1. 实测：现在到底什么样

真机 443×984（dpr 2.4375）。布局已经是自适应的，不是"桌面版缩放"：

```
pI_x6G_frame            443 x 985
├── pI_x6G_sidebarCol    56 x 985   x=0     ← 恒占 12.6% 屏宽，永不收起
│   └── hHd-Xa_root      56 x 985
│       ├── logoRow      36 x 36    y=18    ← 触控目标 36px（偏小）
│       ├── newSession   36 x 36    y=66
│       ├── regionArea   36 x 811   y=114   ← 36px 宽的会话列表（几乎不可读）
│       └── footArea     36 x 54    y=925
├── pI_x6G_centerCol    387 x 985   x=56
├── pI_x6G_rightbarCol    0 x 985   x=443   ← 已正确折叠
└── pI_x6G_overlayLayer 443 x 985           ← 浮层容器，已在
```

**三个真实问题**（按严重度，不按工作量）：

| # | 问题 | 证据 | 性质 |
|---|---|---|---|
| 1 | 会话列表被塞进 **36px 宽**的栏里 | `regionArea 36 x 811` | **功能不可用** |
| 2 | 侧栏恒占 12.6% 屏宽，主内容只剩 387px | `sidebarCol 56/443` | 布局错误 |
| 3 | **内容被整体右推，左右留白完全不对称** | 左 56px / 右 **10px**，差 46px | 布局错误 |
| 4 | 触控目标 36px，低于 44px 人体工学下限 | `logoRow/newSession/regionArea` 均 36 | 可用性 |

第 3 条是**截图之后才量出来的**，比看上去更糟：443px 的屏上，内容左边空 56px、右边只剩 10px。
画面在视觉上是歪的 —— 因为它仍在为一条不该占位的栏留地方。

**顺带纠正一个我先前的错误结论。** 我在计划里写过"软键盘盖住输入框"，并把它列为唯一阻塞项。
实测下来**不成立**：composer 底边在 611px，而键盘顶边约在 745px，两者根本不重叠。
那张让我误判的截图里，键盘遮住的是**键盘自己的上方区域**，不是输入框。
（CDP 的 `focus()` 不会唤起 Android 软键盘，所以精确测量需要真手指 —— 这也是我一度算错的原因。）

> **所以 M2 的阻塞项是左侧那条 36px 的会话栏，不是键盘。**

## 1.5 设计已实测验证（原型已在真机跑通）

设计不靠嘴说。上面那套结构**已经在页面里原型化并量过**：
往页面注入一份 `<style>`，把 `_frame` 改为块流、`_centerCol` 拉满、`_sidebarCol` 提为
`position:fixed` 的屏外抽屉，再加一条 6px 贴边轨道，然后测量：

| 断言 | 现状 | 原型实测 | |
|---|---|---|---|
| 画布占视口宽度 | 0.874 | **1.000** | ✅ |
| 抽屉关 | — | `x=-320, right=0`（屏外） | ✅ |
| 抽屉开 | — | `x=0, right=320`（就位） | ✅ |
| 侧栏触控目标 | 36 × 36 | **44 × 44** | ✅ |
| 左右留白 | 56 / 10（差 46） | 对称（画布满宽后自动居中） | ✅ |

**关键点：整个原型只碰了 `[class*="_frame"]` 这类结构钩子，没有硬编码任何一个哈希类名。**
截图确认：侧栏移出布局后，画布满宽、composer 通栏、内容自然居中。

原型已从页面移除（`m2-probe-style` / `m2-rail` 均已删除，`canvasW` 回到 387、侧栏回到 56）。
它是**设计验证**，不是实现 —— 实现要走 §6 的 slot 叠加路径。

## 2. 设计语言（token）

### 色彩 —— 不新造，只补三档

已有 token 由主题插件在运行时注入，根节点读不到值，所以**新层不硬编码品牌色**，
一律引用现有变量；只在语义缺口处补三档。

| 角色 | 取法 | 理由 |
|---|---|---|
| 画布 / 表面 | `--dsh-bg` / `--dsw-elevation-panel` | 沿用，不重定义 |
| 主文字 / 次要 / 三级 | `--dsh-label-primary/secondary/tertiary` | 沿用 |
| 描边 | `--dsw-elevation-stroke-color` | 沿用 |
| **抽屉遮罩** | `color-mix(in srgb, #000 38%, transparent)` | **新增**：现有系统没有全屏遮罩档 |
| **贴边轨道** | `color-mix(in srgb, currentColor 12%, transparent)` | **新增**：抓握提示，`currentColor` 保证跟主题走 |
| **主操作** | `--dsh-brand` | 沿用（那个蓝色圆钮已经是它） |

**刻意不做的事**：不引入第二种强调色、不加渐变、不加阴影堆叠。
boldness 只花在一处（见 §4）。

### 字体 —— 沿用系统栈，只定尺度

系统栈已经为中文优化过（`PingFang SC` / `Microsoft YaHei`），换字体会同时破坏
38 个插件的排版假设。所以**只定移动端尺度**，且以**触控可读性**而非"设计感"为依据：

| 角色 | 值 | 依据 |
|---|---|---|
| 输入框正文 | **16px / 1.5** | 低于 16px 会触发移动端自动缩放 |
| 会话标题、正文 | 15px / 1.55 | 443px 宽下中文约 26 字/行，落在舒适区 |
| 会话列表次行 | 13px / 1.45 | — |
| 辅助标签 | 12px / 1.4，**不用全大写** | 全大写是 skill 点名的模板化 tell |

### 布局 —— ASCII 对照

**现状（问题）**：会话栏横插在最左，恒定占位。

```
┌────┬──────────────────────────────┐
│    │                              │
│ 36 │   探索未至之境   [预览版]     │
│ px │                              │
│ 会 │   [workspace ▾] [标准模式 ▾]  │
│ 话 │   ┌──────────────────────┐   │
│ 栏 │   │ 描述你想构建的内容…   │   │
│    │   │ ⊕ ⊘ ⓘ    ▦⌄   (↑)   │   │
│    │   └──────────────────────┘   │
│    │                              │
│ ⚙  │        （大片空白）           │
└────┴──────────────────────────────┘
  12.6% 屏宽被永久占用，且列表只有 36px 宽读不了
```

**设计（全宽画布 + 贴边轨道 + 抽屉 + 底部停靠）**：


## 3. 排版与对齐

- **左对齐为主**，画布内边距 16px（原 12px），因为 443px 下每像素都贵；
- 会话列表项 **48px 行高**（原 36px 目标）；
- composer 与画布同宽对齐，不缩进 —— 它是主角，不该看起来像附属控件；
- **不加编号、不加 eyebrow 标签、不给链接加 `→`**：skill 点名的模板化 tell，且此处无序列语义。

## 4. 原则：boldness 只花在一处

**唯一的记忆点 = 输入框正上方右侧的「会话」按钮。**

一个 28px 高、16px 全圆角的胶囊按钮（图标 + 文字），右对齐贴在 composer 上方 ——
尺寸与圆角**刻意对齐 composer 自己的控件**（模型选择、权限选择都是 28px / 16px），
所以它看起来属于那条工具栏，而不是移植时外挂上去的东西。
点它唤出会话抽屉，点遮罩、按 Esc、或点抽屉里的条目收起。抽屉开启时它淡出。

为什么是它：

1. **它直接解决最痛的问题** —— 会话列表从 36px 宽的不可用状态，变成 320px 的可读抽屉，
   同时把画布从 87.4% 还给 100%；
2. 它**不需要新配色**，只借 `currentColor` 与既有描边色，因此不会和 38 个插件打架；
3. 它**不与系统手势竞争**（见下）；
4. **它在拇指自然落点上**（输入框右侧），单手就能按到。

> **两版已废弃的设计，都记录在此以免重蹈：**
>
> 1. **贴边轨道 + 右滑**：Android 10+ 把屏幕左右边缘留给系统返回手势，系统在手势区内
>    先于页面拿到触摸事件，必然冲突 —— 真机上由用户直接指出（§9.6）。
> 2. **左下角 44×44 悬浮圆钮**：不冲突了，但`position:fixed` 悬浮件与 composer 的流式布局
>    各管各的，且视觉上像外挂组件。
>
> 现在是**流内元素**：它作为 composer 列的第一个子节点，位置由与输入框同一套布局决定，
> 不需要知道 composer 高度或键盘状态（§9.11）。

其余一切保持安静：不加渐变、不加动效装饰、不加第二强调色。
**动效只用于回应人的动作**（抽屉开合、键盘升降），不做入场动画 ——
入场 fade-and-slide 是 skill 点名的"AI 生成感"来源。

## 6. 实现路径（已实测可行，零构建）

**怎么落地** —— 我原本以为要给客户端插件搭一套 TS + tsdown 工具链。实测否定：

```
tsdown / esbuild / rollup / vite / typescript / react   →  全部 ABSENT（引擎树是 --omit=dev）
```

但**产物格式是 factory-CJS**，外部依赖由宿主冻结表解析：

```js
window.__ModuleLoader__.load({ id: "...", factory: (require) => { let react = require("react"); … } });
```

所以可以**手写纯 JS**，落在 `android/plugins/`，由现有 stage 脚本装入 —— **零构建**，
与 `node-pty` / `node-addon-system` 两个 shim 同一套做法。

**挂在哪** —— 不覆盖桌面布局，用**既有扩展点**叠加。实测存在的相关 slot：

```
conversation.input.dock        ← composer 停靠区（底部）
conversation.input.overlay     ← 输入区浮层
conversation.composer          ← composer 本体
conversation.view / conversation.chat.node
sidebar.right.pane.tab / sidebar.right.tab.document
conversation.session.header.actions
```

**这一点很重要**：项目的第一原则是"不 fork 上游包、平台差异全部外置"。
走 slot 叠加与这条原则一致；而去改 `pI_x6G_*` 这类**哈希类名**做 CSS 覆盖则与之相悖，
且上游一改哈希就全碎。

| 事实 | 值 | 影响 |
|---|---|---|
| 客户端行 | 53 | 布局/会话/渲染各自独立 |
| 全图声明 external | 仅 1 个 | `react` 等由冻结表提供，其余内联 |
| CSS 变量 | 440–725，语义命名 | 主题稳定，可引用 |
| 类名 | **哈希**（`pI_x6G_sidebarCol`） | **不可做 CSS 覆盖选择器** |

## 9. 实现记录：三个只有实测才会发现的事实

按踩坑顺序，每条都是"看代码看不出来、只有量了才知道"。

### 9.1 这个界面本来就有移动断点，而且比我的 560px 更激进

`dsh-client-ui-layout` 里写着：

```js
const SIDEBAR_AUTO_COLLAPSE = 1024;
const narrow = viewport < SIDEBAR_AUTO_COLLAPSE;
const sidebarCollapsed = narrow ? !layoutInfo.narrowExpanded : layoutInfo.sidebar === 0;
```

**1024px 以下侧栏一律折成图标轨**，除非 `narrowExpanded` 为真。而它由一个既有 action 翻转：

```js
if (d.layoutInfo.viewportWidth < 1024) d.layoutInfo.narrowExpanded = !d.layoutInfo.narrowExpanded;
```

暴露为客户端服务 `ctx.layout.toggleSidebar()`。

**这一条是整个 M2 的关键。** 我最初只把抽屉的宽度改成 320px —— 截图上抽屉确实滑进来了，
但里面**还是那条 56px 的图标轨、`regionArea` 依旧只放图标**。
因为"宽 320px"和"渲染成列表"是两件事：后者由 `narrowExpanded` 决定。

所以插件必须 `inject: ["layout"]` 并在开合时调用 `toggleSidebar()`。
**没有这一步，抽屉只是把同一个不可用的东西搬了个位置。** 这也是 `inject` 从 `[]` 改成 `["layout"]` 的原因。

### 9.2 这个元素上的 `transform` 是死的，`left` 是活的

抽屉最初用 `transform: translateX(-102%)` + 属性选择器做开合。实测：

- 规则解析正常、选择器命中、`!important` 在位、没有被任何东西压过；
- 但渲染出来的矩阵**一动不动** —— 连**内联 `!important` 的 transform** 也一样，关掉 transition 也一样；
- 同一个元素上 `left` 立刻生效。

改用 `left` 后立即可用。**不要"顺手简化"回 transform。**

### 9.3 两条同权 `!important` 规则，浏览器一直选"关"那条

这是卡最久的一条。开合最终改成：

- **样式表负责停靠**（静态 `left:-320px`）—— 静态规则在首帧前就生效，而从 JS 写的内联偏移
  **首次运行时没能落地，抽屉一开始是开着的**；
- **JS 负责展开**（内联 `left:0px`）—— 内联 important 是全叠层最高来源，压得住样式表。

中途试过"两条同权 `!important` 靠源码顺序决胜负"（基规则在前、开规则在后、探针确认顺序正确），
浏览器仍然解析成关的那条。没有继续深挖根因：内联方案可预测、可解释，而且状态本来就是这个插件自己的布尔值。

### 9.4 遮罩选择器写错了结构

遮罩 append 到 `<body>`，是 frame **祖先的兄弟**，永远不是 frame 的后代。
所以 `[class*='_frame'][open] #scrim` 命中不了任何东西 —— 实测确认元素存在、但开状态传不到。
改用 `body:has([class*='_frame'][open]) #scrim`。现代 WebView 支持 `:has()`
（真机 WebView 151）。

### 9.5 侧栏自身是 56px 宽，不会因为容器变宽而变宽

`sidebarCol` 的宽度是给桌面网格列用的，抽屉滑进来 320px，里面的根节点仍是 56px。
需要 `[class*='_sidebarCol'] > *{width:100%!important}`，
`regionArea` 才拿到 316px，列表才有地方铺开。

### 9.6 左边缘手势与系统返回手势冲突（用户实测反馈）

第一版用"贴边 6px 轨道 + 右滑"唤出抽屉。**这在 Android 上根本行不通**：
Android 10+ 把屏幕左右边缘留给系统返回手势，系统在手势区内**先于页面**拿到触摸事件。
用户反馈"会和手势导航冲突"——准确，我的手势是在和 OS 抢同一条 24px 带。

改为**显式按钮**：底部左侧 44×44 的圆形手柄（拇指区内），带 `aria-label`，
开抽屉时淡出。不再有手势歧义，也不需要"可发现性"提示。

### 9.7 输入框跑到摄像头位置：是我把高度链打断了

用户反馈"输入框太靠上，都到摄像头部位了"。根因是我把 `_frame` 从 `grid` 覆盖成 `display:block`，
于是 `_centerCol` 不再是网格项、`flex:1` 失效 —— 它的高度塌成内容高度（实测 **238px / 985px**），
composer 自然贴在顶部。

修法是补回高度链并加上安全区：

```css
[class*='_frame']{display:flex!important;flex-direction:column!important;
  height:100dvh!important;padding-top:env(safe-area-inset-top,0px)!important;}
[class*='_centerCol']{flex:1 1 auto!important;min-height:0!important;}
[class*='_composerSeat']{margin-top:auto!important;
  padding-bottom:calc(env(safe-area-inset-bottom,0px) + 8px)!important;}
```

用 `100dvh` 而非 `100%`：动态单位会跟随软键盘与地址栏收缩。
实测结果：composer 底边 **985 = 画布底边**（贴合底部），`_frame` 上边距 **48px**（让开摄像头）。

### 9.8 安全区是 48px，但页面没有权利用它

`env(safe-area-inset-top)` 在这台机器上**确实返回 48px**（摄像头挖孔），
但服务端下发的 viewport meta 是 `width=device-width, initial-scale=1` —— **缺 `viewport-fit=cover`**，
页面就没有义务遵守这些 inset，所以内容画到了摄像头下面。

在 `WebViewPolyfills` 里补一个 meta 补丁（`MainActivity.onPageStarted` 注入），
而不去改引擎树里的 `index.html`：这样服务端产物与上游保持逐字节一致 ——
与本项目其他所有平台差异同一原则。

### 9.9 一条被静默吞掉的 CSS 规则（最贵的一个）

抽屉手柄一度完全不工作：`position` 计算值是 `static`、点击无反应。
原因是 CSS 数组里 **composer 那条规则漏了一个 `}`**：

```css
[class*='_composerSeat']{margin-top:auto!important;
padding-bottom:calc(...)!important;      ← 少了 }
#dsh-mobile-ui-handle{position:fixed;...   ← 于是被吞进上一条规则
```

更糟的是 `@media` 块也一起被吞，**浏览器不报任何错**。
（我在排查中还被自己的短横线正则误导过：它没匹配 `HANDLE_ID`，导致"检查通过"是假的。）

现在有两道防线：

- **构建期** `tools/check-plugin-css.mjs`（已接入 `stage-engine.ps1`）：
  括号配平、每条规则可达、手柄规则存在且非 static、尺寸达 44px、抽屉不依赖 transform；
  识别符按**各自声明的真实值**代入，所以检查的是真正会发布的那串 CSS；
- **运行期** 插件把 CSSOM 实际解析出的规则数与源码声明数比对，不一致就 `console.error`。

### 9.10 抽屉"开了立刻又关"：document 级点击处理

手柄终于能点之后，抽屉仍然一闪即关。MutationObserver 显示属性**翻转了两次**。

根因：`onSidebarClick`（"点抽屉里的会话后收起抽屉"）挂在 **`document`** 上，
而手柄自己就是个 `button` —— 它的点击冒泡到 document 后命中 `closest('button')`，
把刚打开的抽屉关掉了。改为把该监听挂在**侧栏元素**上，只有抽屉内部的控件能关它。

**教训**：`document` 级的"点某类元素就做某事"很容易把触发它的那个控件也算进去。

### 9.11 按钮改为 composer 流内元素（用户实测反馈）

用户建议："直接把打开侧边栏按钮放在输入栏的上方右侧，保持风格"。采纳，而且这样更好：

- **位置由布局决定，不由坐标决定**。按钮作为 `_composerSeat`（flex column）的第一个子节点、
  `align-self:flex-end`，就自然落在输入框正上方右侧。不需要知道 composer 高度、也不需要
  知道键盘状态 —— 而这些正是 `position:fixed` 悬浮件必须自己跟踪的东西。
- **风格对齐**：28px 高 + 16px 圆角，与 composer 自己的控件（模型选择、权限选择）完全一致；
  `color:inherit` + `currentColor` 派生的描边与底色，因此跟随主题、不引入新配色。
- 仍然不与系统手势竞争（它是个按钮）。

**这一条也是"实测优先"的又一次印证**：前两版的问题（手势冲突、悬浮件与流式布局脱节）
都不是靠读代码能发现的，是新机上手一眼就看出来的。
