# M0 报告：引擎移植验证

| 项 | 值 |
|---|---|
| 里程碑 | M0（引擎移植验证，无 Android 设备参与） |
| 日期 | 2026-09-28 |
| 结论 | **通过（PASS）**，但**推翻了设计文档 v1.0 的一处关键假设** |
| 验证对象 | `@deepseek-ai/dsh@0.1.5-rc.3`，Node v22.23.1 |
| 复现产物 | `profile/android.patch.yml`、`tools/verify-engine.mjs`、`tools/ws-probe.mjs`、`.m0/m0-report.json` |

---

## 1. 结论摘要

1. **引擎能在"无 Landlock"的前提下完整启动，并跑通浏览器侧的全链路。**
   实测：`dsh web` 绑定端口并打印 `http://127.0.0.1:<port>/?token=...`；
   `GET /?token=` → 303 + `HttpOnly; SameSite=Strict; Max-Age=30d` cookie；
   无 cookie 的 `GET /` → 401；带 cookie → 200 且含 `__DSH_BOOT__`；
   静态资源公开可读；`/api/remote.mux` 的 **WebSocket 升级成功**。

2. **设计文档 v1.0 的 §4.2 草稿有一个致命错误，已修正。**
   原方案写的是"禁用 Landlock 沙箱行（`- id: sandbox / disabled: true`）"。
   实测证明这样做**不是"降级"而是"无法启动"**——因为 shell 提供者依赖 `sandbox`，
   而 `permission-presets` 依赖 `shell`，禁用后整个插件树拒绝激活：

   ```
   Error: dsh: plugin tree failed to load: dsh: 2 entries did not activate
   @deepseek-ai/dsh-pwsh-sandbox: pending (waiting for service: sandbox)
   @deepseek-ai/dsh-permission-presets: pending (waiting for service: shell)
   ```

   **正确做法：保留全部提供者挂载，只把权限策略对钉到 `danger-full-access` + `never`。**
   实测该配置下引擎正常启动。

3. **为什么"保留沙箱却不被 Landlock 挡住"成立**：`dsh-sandbox-local` 的 Linux
   runner 链是 `["bwrap", "landlock"]`，而这条链只在 `confine()`（真正请求约束）时
   才被探测。`danger-full-access` 是"不约束"档，因此根本走不到 Landlock 探测。
   代码依据：`dsh-sandbox-local/lib/index.js` 的 `RUNNER_CHAINS`、`defaultProbeBwrap`、
   `launcherPath`，以及 `node-addon-system/lib/index.js:46` 的平台化包解析
   （`node-addon-system-${process.platform}-${process.arch}`，无 android 变体）。

4. **权限策略对必须成对覆盖。** 只改 `sandbox-policy` 会让 `permission-presets`
   构造失败：

   ```
   permission: composed sandbox and approval defaults match no preset;
   configure defaultPreset explicitly
   ```

   因为该校验要求"沙箱 + 审批"的默认组合必须命中某个预设。因此
   `sandbox-policy` 与 `approval` 两行必须一起覆盖（本方案正是复刻
   `DSH_PERMISSION_MODE=danger-full-access` 在上游组合里的既有行为）。

5. **剩余唯一未解风险：`flock`。** `dsh-session-persistence-jsonl` **静态 import**
   `@deepseek-ai/node-addon-system/flock`，而该模块在
   `process.platform === 'android'` 时会抛 `ERR_FLOCK_UNSUPPORTED_PLATFORM`
   （只接受 `linux` / `darwin`）。好消息：绑定是**惰性加载**的，所以
   import 阶段不炸、引擎能启动；坏消息：**第一次会话加锁时才触发**，
   会直接影响会话写入。见 §4。

## 2. 实测证据

### 2.1 能力基线（Node v22.23.1 / win32-x64）

| 能力 | 结果 | 用途 |
|---|---|---|
| `node:sqlite` | ok（`DatabaseSync, StatementSync, constants, backup`） | 会话全文检索（web 组合里 `openAt: never`，惰性） |
| `worker_threads` | ok | code runtime / workflow |
| `child_process` | ok | shell 工具 |
| WebCrypto / `fetch` / `AbortSignal.timeout` | ok | 通用 |

> Android 侧需用 arm64 libnode 重跑同一套断言（`tools/verify-engine.mjs` 的
> `--- capability baseline ---` 段），这是 M1 的第一项检查。

### 2.2 三次启动实验

| # | 配置 | 结果 | 说明 |
|---|---|---|---|
| 1 | 原样 web profile（无 patch） | ✅ 启动，`http://127.0.0.1:63393/?token=...` | 证明 `DSH_HOME` 指向工作区后引擎可跑；作为对照基线 |
| 2 | `sandbox` 行 `disabled: true` | ❌ 启动失败 | 2 个条目未激活，见 §1.2 |
| 3 | **保留全部提供者 + 策略对钉 `danger-full-access`/`never`** | ✅ 启动，`http://127.0.0.1:65249/?token=...` | **Android 采用方案**，并据此后端完成下列全部验证 |

### 2.3 浏览器侧全链路（对实验 3 的引擎）

```
GET /?token=<token>   -> 303 -> /
cookie dsh-auth-...   HttpOnly=true  SameSite=Strict  Max-Age=30d  Secure=false
GET /      无 cookie  -> 401
GET /      带 cookie  -> 200   27205 bytes   __DSH_BOOT__ 存在
静态资源              -> 200   555959 bytes
WS /api/remote.mux    -> open（升级成功）
```

这条链路正是 Android WebView 将要走的路径，因此**"WebView 加载
`http://127.0.0.1:<port>/?token=...` 即可完成认证"在协议层面已被证实**。
（WebView 自身的 cookie 行为仍需真机确认，见 §5。）

### 2.4 组合树对比（`--dump-config`）

| 树 | 行数 | 启用 | Android 下被禁用 |
|---|---|---|---|
| 基线（无 patch） | 152 | 126 | — |
| `android.patch.yml`（守卫在 win32 为 false） | 152 | 126 | 无（守卫生效，桌面运行零影响） |
| `android.patch.yml` + `--simulate-android` | 152 | 123 | `pwsh-sandbox`、`open-in-app`、`directory-picker` |

注：`pwsh-sandbox` 在 Android 下被禁用是**正确结果**（上游基线的
`!!js process.platform !== 'win32'` 条件所致），对应地 `bash-sandbox` 在
Android 下是**启用**的（其条件为 `!== 'win32'`）。

### 2.5 静态提供者图（仅供参照，不作为判据）

`tools/verify-engine.mjs` 会从 `static inject` / `super(ctx,"name")` 推断依赖图。
它**不可靠**：健康的基线树也会报出约 20 个"缺提供者"（例如
`modules needs 'loader'`、`workspace-files needs 'fs'`），因为不少服务是通过
`super(ctx)` + 内部名称动态注册的，正则抓不到。因此报告里该段标记为
**ADVISORY**，只应比较两棵树之间的**差量**，最终判据是真实启动 + HTTP 流程。

## 3. 对本项目架构的影响

| 设计文档章节 | 原内容 | M0 后的修正 |
|---|---|---|
| §4.2 profile 设计 | "禁用 Landlock 沙箱行" | **改为保留 `sandbox` 行，仅钉策略对**。`android.patch.yml` 已按此重写 |
| §4.3 依赖审计 | Landlock 列为"阻塞项，通过禁用解决" | 修正为"**不可禁用**（会破坏依赖图）；通过 full-access 档绕过其探测" |
| §6 里程碑 M0 | "验证 flock / sqlite / worker_threads / sharp 四项" | flock 已定性（见 §4），sqlite/worker_threads 已确认可用；**sharp 仍未验证**（需要真实图片附件流程） |
| §7 风险 R2 | flock 风险 | 升级为**已确认的存在性风险**，并给出两种缓解 |
| §5.4 裁剪项 | 曾考虑裁掉 permission 面板 | 无需裁剪：`permission-presets` 保持激活，面板可用 |

**新的关键结论：Android 移植不需要"删掉沙箱"，只需要"永远不使用约束档"。**
这比原计划简单得多——无需替换 shell 提供者，也无需改动依赖图。

## 4. 未解风险：会话持久化的 flock

**事实链**（全部有代码依据）：

1. `dsh-session-persistence-jsonl/lib/index.js` 第 11 行是**静态 import**：
   `import { tryLockExclusive } from "@deepseek-ai/node-addon-system/flock";`
2. `node-addon-system/lib/flock.js` 的注释明确写着
   "Lazy POSIX flock entry; **importing it does not load a native addon**"，
   因此这条 import 在 Android 上不会立刻失败——**这就是实验 3 能启动的原因**。
3. `loadBinding()` 在**首次 `tryLockExclusive()` 调用时**执行，且：
   ```js
   if (platform !== 'linux' && platform !== 'darwin') {
     throw ... code: 'ERR_FLOCK_UNSUPPORTED_PLATFORM'
   }
   ```
   Android 上 `process.platform === 'android'`，**必然命中此分支**。
4. 该包的分发方式是 `optionalDependencies` 里的预编译平台包
   （darwin-{arm64,x64}、linux-{x64,arm64}-gnu、win32-msvc），**没有 android 变体**。
5. 上游代码里有一处提示其设计意图：浏览器 worker 场景会
   "**stub 掉原生 flock 入口为立即成功**，因为它是单进程的，进程内写声明已排除所有写入者"。
   手机端同样是单进程，因此该理由**在 Android 上同样成立**。

**影响**：会话首次加锁时 `tryLockExclusive` 会 reject（异步，不会同步抛出）。
后果可能是会话创建失败，也可能被持久化层的错误处理吸收——**目前无法从桌面判定**。

**两种缓解（M1 决策）**：

| 方案 | 做法 | 代价 | 评价 |
|---|---|---|---|
| A. 原生移植 | 用 NDK 为 `node-addon-system` 增加 android-arm64 目标（`src/flock.c` 仅 5.7 KB，是薄封装）或自建等价 addon | 需维护一个原生构建目标 | **推荐**：根治，且顺带解决 `main.c` 的 landlock 启动器（虽然后者我们用不到） |
| B. 复用上游 stub 思路 | 在 Android profile 里注入一个把 flock 视为立即成功的接缝（等价于上游浏览器 worker 的做法） | 需要上游暴露接缝，或打一个小 patch | 轻量，但偏离"零改动上游"原则 |

> 注意：**方案 B 不需要真的加锁**。手机端引擎是单进程、单用户，
> 上游自己在浏览器 worker 里就是这么处理的，因此这不是"降低安全等级"，
> 而是"与上游既有先例一致"。

## 5. 仍需真机（arm64）确认的项

| # | 待确认 | 为什么桌面测不了 |
|---|---|---|
| 1 | arm64 libnode 具备 §2.1 的全部能力 | 需要目标运行时 |
| 2 | `dsh-sandbox-local` 在 Android 上能**构造**成功（构造函数会读平台配置，可能引用 `node:os`/平台分支） | 需要 Android 平台 |
| 3 | 首建会话时 flock 的实际表现（§4） | 需要产生真实会话 |
| 4 | WebView 对 `127.0.0.1` 的 cookie 接受度与 WS 长连接稳定性 | 需要 Android WebView |
| 5 | `sharp` 在 Android 上的行为（WASM 回落是否可用） | 需要真实图片附件流程 |
| 6 | 冷启动耗时与解包耗时 | 需要设备 |
| 7 | `node:sqlite` 可用性对全文搜索的影响 | 需要 arm64 libnode（若不含 sqlite 则该功能降级，不影响启动） |

## 6. 复现步骤

```powershell
# 0) 准备：把 DSH_HOME 指向工作区（否则沙箱会拒绝写 %USERPROFILE%\.dsh）
$env:DSH_HOME = "D:\Work\DSHapk\.m0\dsh-home"
$dsh = "C:\Users\yue\AppData\Local\npm-cache\_npx\1e7f6d9597241db0\node_modules\.bin\dsh.cmd"
Set-Location D:\Work\DSHapk\.m0\workspace

# 1) 导出组合树（守卫在桌面为 false，因此桌面运行零影响）
& $dsh --profile web --patch ..\..\profile\android.patch.yml --dump-config > ..\tree-android-guarded.yml

# 2) 静态检查 + Android 模拟（不启动引擎）
node ..\..\tools\verify-engine.mjs --tree ..\tree-android-guarded.yml --simulate-android

# 3) 真实启动（背景任务），记录打印出的 URL
& $dsh --profile web --patch ..\..\profile\m0-full-access.patch.yml --no-open --port 0

# 4) 用同一个 URL 做判据验证（engine-up 表示已观察到启动成功）
node ..\..\tools\verify-engine.mjs --tree ..\tree-android-guarded.yml --engine-up --url "<上一步的 URL>"

# 5) 传输层与信任栅栏
node ..\..\tools\ws-probe.mjs "<上一步的 URL>"
```

`m0-full-access.patch.yml` 是 M0 的实验覆盖层（等价于 Android 守卫分支的实际取值），
`android.patch.yml` 是正式产物（带平台守卫）。两者应保持语义一致。
